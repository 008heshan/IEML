# IEML 设计系统规范

> 设计定位：**克制的现代感** — 参考 Linear / Raycast / Arc 的视觉语言
> 核心原则：层次靠光影与间距，不靠花哨装饰；动效短促精准，不喧宾夺主。

---

## 1. 设计原则

| 原则 | 说明 | 反面案例 |
|---|---|---|
| **内容优先** | UI 让位于游戏封面、版本名、进度这些真实内容 | 大面积渐变装饰压过内容 |
| **安静的高级感** | 用低饱和色 + 微妙明暗层次建立质感 | 高饱和撞色、霓虹光晕 |
| **反馈即时** | 任何操作 100ms 内必须有视觉反馈 | 点击后无响应靠猜 |
| **动效克制** | 转场 150–250ms，缓动自然；不用弹跳、旋转等炫技 | 卡片飞入、loading 转圈乱飞 |
| **密度合理** | 桌面端信息密度可高，但要留呼吸感 | 元素挤成一团 |
| **平台无感** | 三平台视觉一致，仅窗口控制区适配系统习惯 | 各平台长得像两个软件 |

## 2. 色彩系统

采用 **深色为默认主题**（游戏启动器的使用场景多在弱光环境，且深色更显质感），浅色为可选项。

```

  --bg-surface   #111419   主内容区面板
```

### 2.3 主题切换

用 CSS 变量 + `data-theme` 属性，切换**零重渲染**：

```css
:root[data-theme="dark"]  { --bg-base: #0B0D10; /* ... */ }
:root[data-theme="light"] { --bg-base: #F7F8FA; /* ... */ }
```

支持 `跟随系统`（`prefers-color-scheme`）/ 强制深色 / 强制浅色三档。

## 5. 阴影与层次

深色主题下阴影极易失效（黑底黑阴影），所以**主要靠边框 + 明度差建立层次，阴影只做轻微托底**：

```
--shadow-sm   0 1px 2px rgba(0,0,0,0.3)
--shadow-md   0 4px 12px rgba(0,0,0,0.35)
--shadow-lg   0 8px 28px rgba(0,0,0,0.45)
--shadow-xl   0 16px 48px rgba(0,0,0,0.55)    弹窗
--shadow-glow 0 0 0 3px rgba(91,141,239,0.25) 聚焦态

层次公式（深色）
  弹窗 = bg-overlay + border-default + shadow-xl
  卡片 = bg-raised  + border-subtle  + shadow-sm
  面板 = bg-surface + border-subtle
```

**毛玻璃**（仅用于侧边栏 / 顶栏 / 弹窗背景，勿滥用）：
```css
background: rgba(17,20,25,0.72);
backdrop-filter: blur(20px) saturate(180%);
```

## 6. 动效规范

```
时长
  --dur-instant  80ms    按压、勾选
  --dur-fast     120ms   悬停、颜色变化
  --dur-base     180ms   展开、淡入淡出
  --dur-slow     260ms   页面转场、面板滑入

缓动
  --ease-out     cubic-bezier(0.16, 1, 0.3, 1)      进入(快出慢停, 最常用)
  --ease-in-out  cubic-bezier(0.4, 0, 0.2, 1)       状态切换
  --ease-spring  cubic-bezier(0.34, 1.4, 0.64, 1)   轻微回弹(仅用于强调操作)

规则
  ✓ 悬停只改背景/边框/文字色，不位移
  ✓ 面板滑入用 transform + opacity，不用 width/height(触发重排)
  ✓ 进度条变化用线性过渡，不用弹性
  ✓ 尊重系统「减少动态效果」设置: @media (prefers-reduced-motion: reduce) { 全部动画降至 0.01ms }
  ✗ 禁止：loading 无限旋转超过必要范围、卡片飞入、无意义弹跳
```

### 7.3 侧边栏导航（★ 第十三轮改为「正副级页面」）

**这是全应用唯一的导航控件**，一级与二级**共用同一条 218px 侧栏**。

```
宽 218px（< 980px 折叠为 60px 图标模式）

【一级】进入版本之前
  顶部  应用 Logo + 名称（在顶栏）
  中部  4 项，无分组：
          启动        当前选中版本的启动按钮 + 状态
          版本列表    已装版本（行尾徽标显示数量）
          下载        游戏版本 / 加载器 / 整合包
          设置        全局设置
        高 34px，圆角 8px，图标 17px + 文字 13px
        默认 text-secondary；悬停 bg-hover + text-primary
        选中 accent-subtle 背景 + accent 文字
  底部  正在运行的游戏状态（仅运行中出现）

【二级】进入某个版本之后（整条侧栏被替换）
  顶部  ← 返回版本列表
        版本卡：版本名 / MC 版本 / 加载器徽标
  中部  概览 · 设置 · Mod 管理 · 日志
        （Mod 管理带数量徽标）
  底部  常驻主按钮「启动这个版本」/「停止游戏」

顶栏（48px）：品牌 · 面包屑「版本列表 › 版本名」· 任务中心 · 主题开关
```

**为什么二级要"替换"一级而不是并排成两栏**

并排会变成"左侧两栏导航"：218px 的侧栏塞不下，而且用户分不清哪一栏是全局、
哪一栏属于当前版本。替换之后，「我在第几层」由**侧栏本身**回答，
不再需要额外控件（旧版顶栏那个 340px 的实例切换器因此被删除）。
完整推演见 ADR-032。

**已删除的三个东西（第十三轮）**

| 删掉 | 原因 |
|---|---|
| 顶栏实例切换器 | 侧栏顶部的版本卡已经表达了"当前是谁"，再挂一个下拉是重复且制造疑虑 |
| 主页的实例网格 | 选版本用下拉更省地方；浏览版本去「版本列表」 |
| 一级入口「实例设置 / 日志 / 整合包」 | 前两个是**某个版本**的属性，应属二级；整合包回到「下载」页签 |

**导航项命名铁律**：
**每个导航项的文字，必须等于它对应页面的 `h1` 标题。**
不允许出现「入口叫 A、页面叫 B」的情况——用户会认为功能放错了地方。

**「设置」在一级与二级里同名，但不是一个东西**：
一级「设置」= 全局（影响所有版本）；二级「设置」= 只作用于当前打开的那个版本。
两者的区分靠**上下文**（二级页顶部就是版本名）与**页内文案**
（二级设置页首句明写"以下设置只作用于「星河整合包」"），
不再靠名字不同来区分。完整推演见 7.18、ADR-028、ADR-032。

### 7.9 组合选择——三层结构（★ 本项目核心组件，易错点）

「创建实例」页面的加载器选择**必须按三层结构呈现**，不能做成一组并列的复选框。这是技术事实决定的，不是设计偏好。

#### 为什么不能是多选

| 错误做法 | 后果 |
|---|---|
| 六个加载器全做成复选框 | 用户能勾出"Fabric + Forge"这种**物理上不存在**的组合 |
| 基础加载器和叠加层混在一起 | 概念层级混乱，用户不知道 OptiFine 和 Forge 不是一类东西 |
| 不体现 API 前置包 | 用户不知道 Fabric API 被装进去了，看到 mods 文件夹里多出东西会困惑 |

#### 三层结构定义

```
① 基础加载器（Base）—— 单选，四选一，严格互斥
   Forge / NeoForge / Fabric / Quilt
   用 radio（圆形），因为它是一次性决策

② 附加组件（Addon）—— 多选，受约束
   OptiFine / LiteLoader
   用 checkbox（方形），因为可叠加
   可用性随基础加载器实时重算，不可用则置灰 + 写明原因

③ API 前置包（API）—— 只读
   Fabric API / QFAPI
   随基础加载器自动决定，用虚线框 + 「必需」标签展示
```

#### 组件规范

```
基础加载器项（单选行）
  高 ≈ 52px，border 1.5px，radius 10px，padding 11px 13px
  结构  圆形单选钮(17px) + 名称(13px/600) + 描述(11px/tertiary)
  选中  border-accent + accent-subtle 背景 + 名称变 accent + 圆点填充
  禁用  opacity 0.42

附加组件项（多选卡片）
  两列网格，gap 9px，卡片 padding 12px
  结构  方形复选框(17px) + 名称(13px/600) + 描述(11px) + 可选警告条
  状态
    默认  border-subtle，bg-raised
    悬停  border-strong
    选中  border-accent 1.5px + accent-subtle 背景 + 名称变 accent + 复选框填充
    禁用  opacity 0.45 + 复选框边框改虚线 + **必须展示禁用原因**

API 前置包项（只读）
  虚线边框（border-dashed）表示"不可交互"
  结构  图标(26px) + 名称(12.5px/600) + 说明(10.5px) + 「必需」徽标
  空态  显示"当前配置无需额外 API 包"
```

**展开式子项**：勾选后在容器下方展开一行，包含该项的版本下拉 + 推荐标记。
展开用 `display` 切换 + fadeUp 180ms，占整行（`grid-column: 1/-1`），不推挤其他内容。

#### 约束矩阵（必须实现，且放在 Rust 侧）

| 基础加载器 | OptiFine | LiteLoader |
|---|---|---|
| **无（原版）** | ✅ **允许**（Patcher 打补丁） | ❌ 需 Forge 作为基座 |
| Forge | ✅ 允许（1.13~1.14.3 除外，且需过版本号四级判定） | ✅ 允许 |
| Fabric | ⚠️ 允许（1.14~1.20.4，桥接包 **OptiFabric 要玩家自己下**；1.14~1.15.2 用 Origins）；**MC ≥1.20.5 禁止** | ❌ 需 Forge |
| Quilt | ⚠️ 允许（同上，桥接表只按 MC 版本判，与基座无关） | ❌ 需 Forge |
| NeoForge | ❌ **不兼容** | ❌ 需 Forge |

> **重要更正（第四轮）**：上一版这里写的是「无（原版）→ OptiFine ❌ 无依附对象」，这是**错的**。
> OptiFine 能独立装在纯原版上，而且这是它最主流的用法之一（只要光影不要 Mod 的玩家都这么用）。
> 详见 [`DECISIONS.md` ADR-003](./DECISIONS.md)。
>
> **再次更正（第六轮）**：上一条更正里的「**文件覆盖 + 类替换**」也不够准确。
> 源码事实是：现代版 OptiFine 会调用自带的 `optifine.Patcher` 程序，
> **以原版 jar 为输入做字节码级补丁**，产出物落在 `libraries/optifine/OptiFine/<MC版本>_<OF版本>/`；
> 只有老版本 installer 才是「直接复制文件」。所以 UI 文案不要写「覆盖原版文件」，
> 统一写「将对原版 jar 打补丁」，跟事实一致。

**纯原版 + OptiFine 时的 UI 表现**：OptiFine 恢复为可用状态，并在其下方显示
**信息色（非警告色）**的说明「将对原版 jar 打补丁安装，无需加载器」。
用信息色而非警告色的原因是——这是**合法且常见**的组合，不该让用户觉得有问题。

#### 三条交互铁律

1. **切换基础加载器时，附加组件可用性必须立即重算**，不可用的自动取消勾选。
2. **禁用必须给理由**，且理由要具体：写"NeoForge 与 OptiFine 不兼容"，不写"不可用"。
   - 反面：OptiFine 直接消失，用户以为启动器不支持
   - 正面：置灰 + 具体原因，用户理解为什么
3. **要用户自己做的事必须明示**：需要桥接时显示信息条「需要桥接包 OptiFabric —— **要你自己下载**」并给出下载地址，API 包列在只读区。
   - ★ 反过来：**不许写「将自动安装」**，除非生产路径真的有下载它的代码。桥接包就是反例 —— `bridgeFile()` 只存在于浏览器演示模式，界面上写「会自动装」骗了用户一整轮（见 ADR-046）。

#### 关键设计原则

**校验逻辑只实现一次，放在 Rust 侧。** 前端只做两件事：把用户选择发过去、把结果渲染出来。这样不会出现"前端以为能装、后端装不了"的不一致。

**为什么"自动安装"要单独列出来而不是静默处理**：用户装完游戏打开 mods 文件夹，看到莫名多出的 Fabric API 会困惑"这东西哪来的、能不能删"。提前明示反而建立信任——这也延续了"点击前就知道会发生什么"的原则。

### 7.10 拖拽导入遮罩

```
触发   文件拖入窗口任意位置
遮罩   rgba(11,13,16,0.82) + blur(10px)
容器   440px 宽，accent 虚线边框 2px，radius 18px
内容   上传图标 44px + 标题 17px + 说明 12.5px + 支持的格式标签组
动效   fadeUp 160ms
关闭   拖出窗口 或 松开文件
```

**实现注意**：`dragenter`/`dragleave` 会在子元素间反复触发，必须用计数器（depth）而非布尔值判断，否则遮罩会闪烁。

**类型判定顺序（必须按此顺序，错了会误判）**：

```
第 1 步  整合包？  zip 内有 manifest.json / modrinth.index.json
第 2 步  Mod？     zip/jar 内有 fabric.mod.json / META-INF/mods.toml
                  / neoforge.mods.toml
第 3 步  光影包？  zip 内有 shaders/ 目录
第 4 步  资源包？  zip 内有 pack.mcmeta
```

**为什么必须按这个顺序**：整合包里也含有 `mods/` 目录。如果先判 Mod，
会把一个整合包误判成单个 Mod，然后装错位置。**必须先判整合包。**

### 7.13 备份时间线与回滚

```
时间线项  高约 46px，底部 1px 分隔线（最后一项无）
  圆点  8px 圆形；普通项 bg-active 底 + border-strong 边；
        最新项 accent 底 + accent 边 + 3px accent-subtle 外发光
  标题  12.5px / 600
  副行  11px / text-tertiary，含「时间 · 存档数 · 配置项数 · 体积」
        其中体积用 text-secondary + 600 强调（让用户直观看到增量很小）
  按钮  右侧「预览」ghost + 「回滚」secondary
```

**回滚必须二次确认且自动留退路**：点击「回滚」后，先提示
「正在创建回滚前快照…」，再执行。**用户回滚后如果再后悔，还能回到回滚前的状态。**
这个设计不能省——否则一次误操作就永久丢失进度。

**说明文案**：卡片底部必须解释为什么备份这么小——
「只备份存档与配置；Mod 列表仅记录清单（回滚时按需重新下载），所以单次备份只有几 MB」。
否则用户会怀疑「才 2.8 MB，是不是没备份全？」

### 7.14 崩溃分析弹窗

```
布局    宽 620px，最大高 70vh
结构
  ├─ 顶部   结论摘要（人话，如"游戏因内存不足而崩溃"），字号 15px/600
  ├─ 中部   可能原因列表，每项含：原因文字 + 建议动作按钮
  ├─ 折叠   原始日志 / 堆栈（默认收起，点击展开）
  └─ 底部   [导出报告] [查看日志] [关闭]

配色    结论区用 danger-subtle 底（崩溃是负面事件）
        建议动作按钮用 accent
```

**铁律：首屏必须是「原因 + 建议动作」，绝不能是堆栈。**
用户打开弹窗第一眼看到的东西，决定他会不会继续用这个启动器。

**导出报告前必须脱敏**，并告知用户做了什么：

```
┌─────────────────────────────────────────────┐
│  即将导出崩溃报告                            │
│                                             │
│  包含                                      │
│    · 分析结果                                │
│    · latest.log / crash-report              │
│    · 实例配置 · Mod 列表 · 系统信息          │
│                                             │
│  已脱敏                                    │
│    · 玩家名 → <player>                      │
│    · UUID → <uuid>                          │
│    · 检测到并移除 2 处令牌                    │
└─────────────────────────────────────────────┘
```

这一步不能省。日志里出现自己的正版账号名或 token，用户会介意——
**在导出前主动告诉他处理了什么，比事后被质疑要好。**

### 7.15 Mod 状态徽标（★ 第六轮新增）

Mod 列表每一项右侧有一个状态徽标，用颜色 + 文字同时表达语义（不依赖颜色单独传达信息）。

| 状态 | 内部标识 | 颜色 | 文案 | 含义 |
|---|---|---|---|---|
| 正常 | `Fine` | 中性（灰） | 无徽标 | 一切正常，不占视觉重量 |
| 已禁用 | `Disabled` | 中性（灰） | 「已禁用」 | 用户手动关闭 |
| 可更新 | `CanUpdate` | 信息（蓝） | 「可更新」 | 有更新版本可用 |
| **可能不兼容** | `MaybeIncompatible` | **警告（黄）** | 「可能不兼容」 | 从元数据推断出的怀疑，**不是判定** |
| 有错误 | `Errored` | 危险（红） | 「有错误」 | 文件损坏 / 解析失败 / 缺失前置 |
| 前置库 | `Library` | 中性（灰） | 「前置库」 | 它是别的 Mod 的依赖，不建议单独动 |

**「可能不兼容」这一档的措辞是刻意的，不能写成「不匹配」或「不兼容」：**

> **★ 2026-09-11 第六轮修正：** 原设计把这一档定为「不匹配」（红），
> 假设我们可以通过读 Mod 元数据主动发现问题。源码研读证明**这个假设不成立**：
>
> - HMCL 的 `FabricModMetadata` **只解析 7 个字段**（`id / name / version / description / icon / authors / contact`），
>   **完全不读 `depends` / `breaks` / `conflicts`**，所以它根本不知道 Mod 要什么 MC 版本
> - HMCL 的 `ForgeNewModMetadata.analyzeLoader()` 读 `dependencies` 数组**只为了判归属**
>   （找 `modId == "forge"` 还是 `"neoforge"`），不校验版本区间
> - PCL2 的 `McMod` **只有 Fine / Disabled / Unavailable 三态**，压根没有「不匹配」这一档
> - 两个启动器**都靠崩溃日志运行时判定**版本不匹配，不做静态预检
>
> 既然业内最好的两个启动器都不敢静态判定，我们如果标红并说「不匹配」，
> 就是在**用一个我们不掌握的信息给出确定性结论**——用户信了，然后发现是误报，信任就没了。
> 所以降级为黄色 + 「可能」+ 可点开解释。

**徽标可点开，展开后必须说明三件事**（这是「可能不兼容」能站得住脚的前提）：

```
┌────────────────────────────────────┐
│  为什么显示「可能不兼容」？          │
│                                    │
│  推断依据                          │
│    · 该 Mod 声明支持 1.20.4         │
│    · 当前实例是 1.21.1              │
│                                    │
│  请注意                            │
│    · 这只是一个提醒，不是结论        │
│    · Mod 可能仍然能正常工作          │
│    · 以实际启动结果为准              │
│                                    │
│  [仍然尝试启动]  [查看 Mod 详情]     │
└────────────────────────────────────┘
```

**筛选器必须同步用这个词**：`全部 / 已启用 / 已禁用 / 可更新 / 可能不兼容 / 有错误 / 前置库`。
不要出现「不匹配」这个筛选项。

相关决策见 [`DECISIONS.md` ADR-019 / ADR-021](./DECISIONS.md)。

### 7.16 「Mod 不自动更新」策略提示条（★ 第六轮新增）

Mod 页面顶部常驻一条**信息色**提示，向用户说明本启动器对 Mod 更新的默认立场：

```
┌─────────────────────────────────────────────────────────────┐
│  ⓘ  Mod 不会自动更新                                          │
│     默认只检查、不自动替换。更新可能改变 Mod 依赖的           │
│     API 或游戏版本要求，导致游戏无法启动。                     │
│                                        [了解更新风险] [不再提示]│
└─────────────────────────────────────────────────────────────┘
```

**为什么值得占这一行位置**：用户从其他软件带来的预期是「Mod 像 App 一样自动更新」，
这个预期本身就是**打崩游戏的头号原因**（用户原话：「模组不是 app，默认更新会导致
模组和 API、游戏版本不匹配」）。与其等出问题了再解释，不如在页面上先把立场说清楚。
`[不再提示]` 会把这个条折叠成一个小图标，不做永久关闭。

批量更新时的提示条（在选中多个可更新 Mod 后出现）：

```
┌─────────────────────────────────────────────────────────────┐
│  3 个可更新，其中 2 个与当前实例（1.20.4 + Fabric）匹配       │
│                                        [批量更新…]  [取消选择]│
└─────────────────────────────────────────────────────────────┘
```

注意文案里的「**其中 2 个匹配**」——不回避有 1 个可能不匹配的事实，
批量更新时那一项要单独标黄并在确认弹窗里被跳过（除非用户勾了「仍然更新」）。

### 7.17 安装配置步骤（★ 第七轮确立 / 第八轮拆分）

> **来源**：用户提出「每个版本都应调一些必要的设置」。
> 原设计的下载中心点「安装」是**直接开下**，不做任何确认——这是个真实的功能缺失。

**为什么必须要有这一步**：MC 的「版本」不是「下载一个程序，装完就跑」，
而是**创建一个拥有独立配置的实例**。下面这几项在安装时定下来最省事：

| 配置项 | 为什么必须在安装时问 | 事后改的代价 |
|---|---|---|
| **实例名称** | 决定数据目录名，改名要挪整个目录 | 重命名 + 修正所有引用 |
| **Java 运行时** | 不同 MC 版本需要不同 Java（见 ADR-013） | 改配置即可，但启动失败时才发现会很难排查 |
| **内存分配** | 影响能否启动 / 是否卡顿 | 改配置即可，相对轻 |
| **版本隔离** | 决定存档、Mod、config 是否与其他实例共享 | **最难改**——要搬存档、搬 Mod、合并 config |

**版本隔离是这里面最要紧的一项**，所以它单独占一个区块、用三档卡片而不是下拉框：

```
┌─ 版本隔离 ─────────────────────────────────────────┐
│  ◉ 自动判定（推荐）         [默认]                  │
│    该目录下有 mods/saves 就隔离，否则共享            │
│  ○ 强制隔离                 [装 Mod 建议]           │
│    独立的 mods / saves / config 目录                 │
│  ○ 不隔离（共享）           [省空间]                │
│    与 .minecraft 共用目录                            │
└────────────────────────────────────────────────────┘
```

**三条安装路径的配置项不同，因为约束不同**（★ 第十轮修订）：

| 路径 | 所在位置 | 可配置 | 只读展示 |
|---|---|---|---|
| 游戏版本 | 下载中心 › 版本页签 → 开弹窗 | 实例名、加载器、附加组件、API 包 | 将下载体积、Java、预计耗时 |
| 加载器 | 下载中心 › 加载器页签 → 开弹窗 | **装到哪个版本**、加载器版本、实例名 | 将自动安装的 API 包 |
| 整合包 | 整合包（独立一级入口） | 实例名、Java、内存、安装位置 | **游戏版本 / 加载器 / Mod 数量**（作者定义，不可改） |

整合包那一栏的只读项用 `border-dashed` + `.pack-lock` 表达「这是别人定好的」——
不是不能改，而是改了就不是这个整合包了。

> **★ 第十轮修订 —— 前半部分配置项已移出**：
> 用户指出「创建实例和下载中心的功能高度重合」。核实后确认：
> 下载中心原有两个 `.setup-panel`（版本 / 加载器），各带一份
> 实例名 + Java + 内存 + 版本隔离，与「创建实例」页和「实例设置」页**三重重复**。
>
> 处理：
> - 下载中心里**两个 `.setup-panel` 全部删除**，页面级重复的内存滑块与实例名输入框一并删除
> - 「创建实例」从独立页面**降为弹窗**（ADR-031）
> - **Java / 内存 / 版本隔离这三项不再出现在创建流程中**，
>   创建时按 Mod 数量自动估算默认值，之后统一去「实例设置」改
>
> 因此上表中「Java、内存、版本隔离」不再是各路径的配置项——
> **它们在实例设置页里，且只在那里**。这就是 7.20「同一件事只在一个地方可编辑」。
>
> 保留 `.setup-panel` 组件的只有一个场景：**整合包**（因为它确实需要
> 在安装前确认名称与安装位置，且整合包的版本/加载器是作者定好的，不可改）。

> **★ 第八轮修正**：整合包最初被合并进「下载中心」当第三个页签。
> 用户指出这一步做错了（见第 9 章），整合包现已**拆回独立一级入口**。

**交互规范**：

1. 配置面板**内联展开**在列表上方，不用弹窗——弹窗会遮住用户刚选的那个版本，失去上下文。
   **例外（第十轮）**：「创建实例」本身是弹窗，因为它包含版本列表本身，
   内联展开会让列表页结构崩塌。两者不矛盾——判断标准是「配置的对象是不是当前页面的列表项」。
2. **同时只展开一个**面板；选另一个卡片时自动收起前一个。
   切换一级入口（`go()`）时必须收起全部面板，避免跨页残留。
3. 展开后 `scrollIntoView({block:'center'})`，避免面板出现在视口外用户看不见。
4. 所有字段**预填合理默认值**（ADR-007），用户直接点确认也能走通。
5. 但凡用户改动过某个区块，该区块打上 `.changed` 标记（右上角「已改」小标签），
   让用户一眼看出哪些不是默认值、哪些是自己动过的。
6. 底部摘要必须显示**将下载体积 + Java + 预计耗时**，让用户在点确认前就知道会发生什么。
7. 主按钮文案是「**确认并开始安装**」（整合包）/「**创建并安装**」（创建实例弹窗），
   不是「安装」——明确这是一个有前置确认的动作。

相关决策见 [`DECISIONS.md` ADR-005 / ADR-007 / ADR-031](./DECISIONS.md)。

### 7.18 实例设置的作用域表达（★ 第九轮新增）

> **来源**：研读 PCL2 版本设置模块时发现——它的「全局设置」和「版本设置」
> **在界面上长得几乎一模一样**，用户极易搞混"我改的是全局还是这个版本"。
> PCL2 自己也知道，用了三重手段补救（见 `LAUNCHER_SOURCE_STUDY.md` 13.1）。

**IEML 的四层防线**（比 PCL2 多一层）：

**① 入口名带作用域**
侧边栏「设置」= 全局；实例详情里的入口叫「**实例设置**」。不得都叫「设置」。

**② 页面顶部常驻作用域提示条**
```
┌────────────────────────────────────────────────────────┐
│ ⓘ  以下设置只作用于「星河整合包」，不影响其他实例       │
└────────────────────────────────────────────────────────┘
```
用 `--color-background-info` 底色 + `--color-text-info` 文字，与内容区明显区分。

**③ 每个可继承字段显示「配置来源」双态标签** ← IEML 比 PCL2 更彻底的一层

PCL2 的做法是「空值 = 跟随全局」，但**用户看不出"我是留空了还是删掉了"**。
IEML 改为显式的两个状态：

```
内存分配          [跟随全局]          ●
Java             [已覆盖]    ○  17.0.10
版本隔离          [跟随全局]          ●
```

| 标签 | 样式 | 含义 |
|---|---|---|
| `跟随全局` | 中性灰底、无边框 | 该项由全局设置决定 |
| `已覆盖` | 强调色底 + 左侧圆点 | 该项已被实例单独设定，全局改动不影响它 |

**交互**：点击标签可在两态间切换，切换时值与标签同时更新。
这比"清空输入框以恢复继承"直观得多——用户不需要知道"空值"这个隐藏约定。

**④ 改动敏感项必须弹警告，且给可逆暗示**

以「版本隔离」为例（照抄 PCL2 的文案结构）：

```
┌─ 警告 ──────────────────────────────────────────────┐
│ 调整版本隔离后，你需要把存档、Mod 等文件手动迁移到     │
│ 新的游戏文件夹中。                                    │
│ 如果发现存档消失，把这项设置改回来就能恢复。           │
│ 如果你不会迁移存档，不建议修改这项设置！               │
│                    [我知道我在做什么]  [取消]         │
└─────────────────────────────────────────────────────┘
```

两个要点：
- **「改回来就能恢复」这句不能省** —— 它把"不可逆的恐惧"降级成"点一下的事"。
  用户不怕改，怕的是改错了回不去。
- **取消时必须回滚控件选择** —— 否则 UI 显示新值、实际设置是旧值，状态不一致。
  PCL2 用 `Static IsReverting` 静态标志阻止回滚再触发 `SelectionChanged` 死循环，
  这个细节必须一并实现。

**实例列表里的作用域提示**：表格中「Java」「内存」等列，若该实例为继承值，
显示为灰色斜体 `17.0.10 (全局)`；若为覆盖值，显示为正常字色 + 小圆点标记。

相关决策见 [`DECISIONS.md` ADR-028](./DECISIONS.md)。

### 7.19 内存分配控件（★ 第九轮新增）

> **来源**：PCL2 的 `PageInstanceSetup` 内存卡片（源码见 `LAUNCHER_SOURCE_STUDY.md` 13.3）。
> 算法整体采纳，可视化方式改为紧凑版（ADR-029）。

**三态单选**：`跟随全局` / `自动配置` / `自定义`（仅「自定义」时滑块可用）。

**紧凑展示**（替代 PCL2 的三段式内存条）：

```
┌─ 内存分配 ────────────────────────────────────────┐
│  ● 跟随全局   ○ 自动配置   ○ 自定义               │
│                                                   │
│  已用 4.7 / 共 7.9 GB   ·   分给游戏 2.5 GB       │
│  ▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░  一行细进度条     │
│                                                   │
│  [滑块 ──────●──────────]  2.5 GB                 │
│  自动配置依据：24 个 Mod + 当前可用 3.2 GB         │
└───────────────────────────────────────────────────┘
```

**「依据」这一行是 IEML 新增的**：PCL2 只给结果不给过程，
用户看到一个数字会怀疑"这是怎么算的"。写清依据（Mod 数 + 可用内存）
让自动值变得可信，也给了用户调它的判断基础。

**显示规则**：
- 三段信息（已用 / 总量 / 分给游戏）**合并成一行**，用 `·` 分隔，
  字号 12px、`font-variant-numeric: tabular-nums`（数字不跳动）
- 进度条只保留**一条 4px 细线**，三段用不同色块区分（已用灰 / 游戏强调色 / 空闲透明）
- **分配值 > 可用内存时**：进度条按可用值画，但文字仍显示真实分配值，
  并追加 `(可用 3.2 GB)` —— 不骗用户，也不画一个物理上不存在的条

**滑块规则**：
- 滑块值是**档位**不是 MB，需分段映射到 GB：
  ```
  档位 0..12   →  0.3 ~ 1.5 GB    (步进 0.1)
  档位 13..25  →  2.0 ~ 8.0 GB    (步进 0.5)
  档位 26..33  →  9 ~ 16 GB       (步进 1)
  档位 34..    →  18 GB 以上      (步进 2)
  ```
- **滑块上限随物理内存动态变化**，不写死
- 数值实时刷新（1 秒定时器），但**只有值真变了才触发过渡动画**——
  否则每秒钟动一次会非常烦人

**自动配置的"依据"文案示例**：
| 情况 | 文案 |
|---|---|
| 可装 Mod | 「依据 24 个 Mod 与当前可用 3.2 GB 内存估算」 |
| OptiFine | 「OptiFine 版本，按 3 GB 基准估算」 |
| 原版 | 「原版游戏，按 2.5 GB 基准估算」 |

相关决策见 [`DECISIONS.md` ADR-029](./DECISIONS.md)。

### 7.20 配置来源可见性（★ 第九轮新增，本项目全局原则）

7.18 的「跟随全局 / 已覆盖」标签不该只出现在实例设置里。
**只要一个值可能来自多个来源，就必须标出它当前来自哪**：

| 场景 | 来源可能 | 表达方式 |
|---|---|---|
| 实例的 Java 版本 | 全局 / 本实例 | `跟随全局` / `已覆盖 17.0.10` |
| 实例的内存 | 全局 / 自动 / 自定义 | `全局值` / `自动值` / `自定义` |
| 实例的版本隔离 | 自动判定 / 手动指定 | 显示「已自动判定为隔离」并注明依据 |
| 下载源 | 全局 / 本次任务 | `跟随全局（BMCLAPI）` / `本次指定` |
| Mod 的启用状态 | 文件系统（唯一来源） | 无需标注——**只有单一来源时不加标签** |
| 整合包实例的 Mod 版本 | 包清单（唯一来源） | 显示「由整合包管理」，更新按钮置灰 |

**原则**：**来源多于一个才标注，单一来源不标注**。
到处加标签会变成噪音，反而稀释了真正需要提醒的地方。

这条原则与第 13 章文案规范里的「给理由，不给黑箱」是同一件事的两面：
- 「给理由」= 说清**为什么是这个值**
- 「配置来源可见性」= 说清**这个值是谁定的**

### 7.21 作用域路由（★ 第十轮新增）

> **来源**：用户指出「创建实例和下载中心的功能高度重合」。
> 解法是把「选择」与「配置」拆开（ADR-031），但**拆开后留下一个空档**：
> 用户点一个「已安装」的版本时，系统默认行为是什么？
>
> 这个组件就是补这个空档的。

**它解决的问题**：下载中心列出的版本里，有些本机已经装了。
此时"点一下"有三种可能的意图，而**两种默认行为都是错的**：

| 默认行为 | 后果 | 判定 |
|---|---|---|
| 直接开下 | 重复下载已有版本 | ✗ 浪费 |
| 默默新建实例 | 凭空多出一个重名实例 | ✗ **最糟** |
| **先问你要做什么** | 用户自己选 | ✓ |

**形态**：内联提示条，插在触发它的那一行下方，`warning` 色系（这是一次需要你决策的岔路，不是错误）。

```
┌───────────────────────────────────────────────────────────────────┐
│ ⚠  Minecraft 1.20.4 已经装过了，你想做什么？                        │
│    这两件事结果完全不同 —— 一个是改现有环境，一个是新建一套          │
│                                                                   │
│    [ 给已有实例装加载器 / 改设置 ]  [ 另建一个新实例 ]  [ 取消 ]     │
└───────────────────────────────────────────────────────────────────┘
```

**规范**：

1. **触发条件**是「该行对应的版本本机已安装」，不是"用户点了某个特定按钮"。
   点击整行即触发，因为用户不会去看按钮上写的是"安装"还是"已安装"。
2. **文案结构固定为「事实 + 后果 + 选项」**：
   - 事实：「Minecraft 1.20.4 已经装过了」
   - 后果：「这两件事结果完全不同 —— 一个是改现有环境，一个是新建一套」
   - 选项：三个按钮，**路径名词必须是目的地页面的名字**（"给已有实例装加载器 / 改设置"、"另建一个新实例"）
3. **同一时间只显示一个**：新的触发会移除旧的，避免堆叠。
4. **切页时自动移除**（在 `go()` 里清）——它属于发起它的那一行，跨页即失效。
5. **第一个选项跳「实例设置」，第二个选项开「创建实例」弹窗**。
   注意第一个选项的**动作是"改"**，所以它不得新建任何东西。

**为什么不用弹窗**：弹窗会遮住用户刚点的那一行，失去上下文；
而且这是一个"分岔"而不是"确认"，内联展示更贴近"从这一行分出去两条路"的心智。

**这个组件是 ADR-031 的最终保证**：
只要用户在岔路口被明确告知两条路通向不同结果，
「下载中心」与「创建实例」相邻陈列就不会造成混淆。

**相关**：[`DECISIONS.md` ADR-031](./DECISIONS.md)、本章 7.17（安装配置步骤）、
第 9 章（信息架构的三路径分工）。

## 9. 信息架构（导航）

**★ 2026-09-11 第十三轮：改为「正副级页面」，一级 7 项 → 4 项。**
起因是用户反馈 **「我倒是喜欢 PCL 的正副级页面，因为它方便，现在这个 UI 特别繁复」**。
完整推演见 ADR-032 与 ADR-033；下面先给当前结构，历史推演留在后面（不再有效但保留教训）。

### 9.1 当前结构（权威）

```
一级（侧栏 4 项，永远是这 4 项）
├── 启动          一颗版本下拉 + 一个启动按钮 + 一行状态（内存 / Java / 上次游玩）
│                 └ 唯一入口：空状态给「去下载游戏」「浏览整合包」
├── 版本列表      一行一个版本（图标 / 名称 / MC+加载器+内存+隔离 / 最近游玩 / 启动 / ⋯）
│                 └ 单击整行进二级页；右上「新装一个」→ 下载页
├── 下载          三个页签：游戏版本 · 加载器 · 整合包
└── 设置          全局：外观 / Java 环境 / 新版本默认值 / 下载 / 账号 / 存储

二级（进入某个版本后，侧栏整条替换）
├── 概览          **全是动作，没有一个是"值"**：
│                 补全文件 · 查看日志 · 图标与名称 · 复制这个版本
│                 + 只读事实表（内存/Java/隔离/Mod/最近游玩/累计时长，每项带"改"）
│                 + 折叠的危险区（删除这个版本）
├── 设置          只作用于当前版本：隔离 / 窗口标题 / Java / 内存
├── Mod 管理      筛选 · 搜索 · 启用禁用 · 更新 · 删除 · 批量
└── 日志          统计 / 崩溃分析 / 导出（脱敏）/ 原始日志 / "怎么看日志"

顶栏：品牌 · 面包屑（仅二级页）· 任务中心 · 主题开关
底部：一级页显示"正在运行的游戏"；二级页显示常驻主按钮「启动这个版本」
```

**三条铁律（违反即 bug，见 ADR-033）**

| # | 铁律 | 反面例子 |
|---|---|---|
| ① | **一个值只能有一个地方能改** | 概览页同时展示可编辑的内存值 + 设置页也能改 → 两处不同步 |
| ② | **导航层级表达作用域，不表达功能分类** | 把「日志」「Mod 管理」放一级 → 用户不知道这是全局日志还是某个版本的 |
| ③ | **派生状态必须随上下文清空** | 切换版本后 Mod 列表仍是上一个版本的 → 概览显示 0、Mod 管理显示 25 |

**一级页 vs 二级页的判断方法**

把候选入口念一遍，问「它说的是启动器本身，还是当前这个版本？」

- 「下载」「设置」→ 启动器本身 → **一级**
- 「Mod 管理」「日志」「这个版本的 Java/内存」→ 某个版本 → **二级**

混在一起时，用户永远无法确定自己改的是全局还是某个版本。

### 9.2 历史推演（第十轮，已失效但保留教训）

> **★ 2026-09-11 第十轮补充：创建实例降为弹窗，侧边栏 8 项 → 7 项。**
>
> 起因是用户指出 **「创建实例和下载中心的功能高度重合」**。
> 核实后确实如此：两者各有一份版本列表、一份加载器选择、
> 一份（实例名 + Java + 内存 + 版本隔离）配置——**四处几乎逐一对应**。
> 加上第九轮新建的「实例设置」页也在管 Java/内存/隔离，**变成三处做同一件事**。
>
> **根因不是"哪里做多了"，而是没分清「选择」与「配置」**：
>
> | | 选择 | 配置 |
> |---|---|---|
> | 对象 | 版本、加载器、整合包 | Java、内存、隔离 |
> | 用户在做的事 | 挑一个 | 定一个值 |
> | 这些对象在用户不操作时存在吗 | **不存在**（只是一次选择的输入） | **存在**（是实例的属性） |
> | 自然归宿 | 列表页 | 设置页 |
>
> 「创建实例」把两者缝在一起，于是它既像列表页（有版本列表）又像设置页（有 Java/内存），
> **必然两头都像，也就必然与两边都重合**。
>
> 这一条至今仍然成立，并被第十三轮沿用：创建实例仍是弹窗，
> 只是唤起它的位置从"版本管理页右上"变成了「版本列表」与「下载」两处。
>
> **第十三轮的追加修正**：第十轮把「配置的唯一编辑入口」定为**一级**的「实例设置」，
> 这是错的——配置属于某个版本，就该待在那个版本的二级页里。
> 一级「设置」只留全局项。

> **★ 2026-09-11 第九轮补充：新增「实例设置」独立一级入口。**
>
> 依据是 PCL2 版本设置模块的研读（`LAUNCHER_SOURCE_STUDY.md` 13.1）：
> PCL2 的「全局设置」与「版本设置」**界面几乎一模一样**，
> 用户在"我改的是全局还是这个版本"上极易搞混——它自己在两处加了强调才勉强缓解。
>
> 我们的解法更彻底：**把两者做成两个不同的一级入口**，
> 并在实例设置页内部用「跟随全局 / 已覆盖」标签（7.18）逐项标出来源。
>
> 为什么不做成「设置页里的一个页签」：因为作用域是**最容易搞错、后果又最重**的一类信息
> （改错隔离方式可能要搬存档）。把它藏进页签会加重这个风险。

> **★ 2026-09-11 修正记录（两阶段）**
>
> **第一阶段 —— 发现命名错误。**
> 起因是用户问「为什么下载中心整合在了整合包栏里」。查下来的结论是：
> **这是一个命名错误导致的信息架构错位，不是布局问题。**
>
> 侧边栏入口原来叫「整合包」，点进去的页面标题却是「下载中心」，
> 里面还并列着「游戏版本 / 加载器 / 整合包 / 下载队列」四个页签。
> 于是产生两个矛盾：入口名（整合包）≠ 页面名（下载中心）；
> 且这个入口名会让用户以为「整合包」是这个页面的主体，其余三个是附属。
>
> **教训**：入口名必须等于页面职责。名字起错时，用户看到的不是"叫法不同"，
> 而是"功能被塞进了别的地方"——即使代码里它们本来就是平级的。
>
> **第二阶段 —— 修正过头，被用户驳回。**
> 第一阶段的修正方案是「改名下载中心 + 把三者收成并列页签」。
> 用户随即指出：**「整合包单开一个选项」。**
>
> 复盘：第一阶段只解决了「名字」，没解决「东西不是一类」。
> 三条路径虽然都是"装东西"，但操作模型有本质差异：
>
> | 路径 | 操作模型 | 用户在做的事 | 失败恢复 |
> |---|---|---|---|
> | 游戏版本 | **用户做一系列选择** | 选版本 → 选加载器 → 配 Java | 中断只需重来 |
> | 加载器 | **用户做一系列选择** | 选目标版本 → 选加载器版本 | 中断只需重来 |
> | 整合包 | **用户挑一个别人做好的结果** | 看描述 → 挑一个 → 确认 | 要**按清单续传** |
>
> 前两者是"配一套环境"，后者是"挑一个成品"——**心智模型不同，就不该在同一个导航层级里**。
> 塞在一起还有一个实际后果：页签栏的空间被三个页签挤满，
> 而整合包真正需要的东西（封面、来源、Mod 数量、加载量提示、排序）根本放不下。
>
> **最终结构**：
> - **下载中心**（一级入口）—— 两个页签：游戏版本 / 加载器 + 下载队列。
>   页签栏右侧加一个「找整合包？→」跳转按钮，防止用户找不到。
> - **整合包**（一级入口）—— 独立成页后才放得下搜索、热门/最新/最多下载排序、
>   版本与加载器筛选、卡片网格、加载量提示。
>
> 三者仍然**共用同一个 `.setup-panel` 配置面板组件与同一条安装流水线**，
> 只是入口位置不同——**组件复用，入口分离**。

**崩溃分析不是独立入口**，而是**从游戏退出事件触发的弹窗**（见 7.14）。
理由：用户崩溃时不会主动去找"崩溃分析"这个菜单，他只会想"为什么突然关了"。
必须**在崩溃发生时主动弹出**，而不是让用户去找。

**为什么「创建实例」不再是独立入口**（第十轮改）：
它原来被提为一级入口，理由是"使用频率最高"。这个判断没错，
但**"频率高"不等于"该占一个入口"**——它频率高恰恰因为它是从别处被唤起的一次性动作。
现在它有 3 个唤起点（版本管理页右上主按钮、下载中心任意行、主页卡片），
比原来"必须先去侧边栏点一下"更近，而不是更远。

**为什么「资源包 / 光影包」不单独开一级菜单**：它们和 Mod 一样都是放进实例目录的文件，本质是同类操作。合并进「Mod 管理」页用标签页区分即可，多开一个菜单反而增加用户的选择负担。

**三个"装东西"入口的分工**（第十轮修订版）：

| 入口 | 形态 | 面向 | 操作模型 | 落点 |
|---|---|---|---|---|
| **创建实例** | **弹窗** | 「我知道我要什么」 | 一页把版本+加载器+附加组件+API 全配好 | 新建实例 |
| **下载中心** | 页面 | 「我先看看有什么」 | 按类别浏览、搜索、筛版本 | **两个出口**：新建实例 / 作用域路由 |
| **整合包** | 页面 | 「我想拿来就能玩」 | 浏览成品包、看作者配好的组合 | **挑结果** |

三者共用同一套约束规则（`VER_META` / `addonCompat` / `apiForBase`），不重复实现。
**注意第十轮的实质变化**：原来三者都叫"入口"，现在只有两个是"入口"，
创建实例是**动作**——这个区别正是重合的解法。

## 10. 无障碍

- **对比度**：正文文字对背景 ≥ 4.5:1，大字号 ≥ 3:1。
- **键盘**：所有功能可纯键盘完成；`Tab` 顺序符合视觉顺序；焦点环始终可见（不得 `outline: none` 而不给替代）。
- **快捷键**：

| 快捷键 | 功能 |
|---|---|
| `⌘/Ctrl + K` | 全局搜索（命令面板） |
| `⌘/Ctrl + N` | 创建新实例 |
| `⌘/Ctrl + ,` | 打开设置 |
| `Enter` | 启动选中实例 |
| `Esc` | 关闭浮层 / 取消拖拽遮罩 |
| `↑ / ↓` | 在版本列表、实例列表间导航 |

- **语义**：用 Radix UI 提供的无障碍原语（dialog/listbox/tabs 的 ARIA 已处理）。
- **减少动效**：响应 `prefers-reduced-motion`。
- **纯键盘操作版本选择**：左侧列表支持方向键移动、`Enter` 选中、`Space` 勾选加载器（复选框原生行为）。

| 项 | 处理 |

## 13. 文案规范

界面文案直接影响"这个软件感觉好不好用"，单独列一节。

| 原则 | 反例 | 正例 |
|---|---|---|
| **说结果，不说过程** | "正在调用 install_profile.json 解析器" | "正在准备 Forge 47.2.0" |
| **给理由，不给黑箱** | "OptiFine 不可用" | "OptiFine 未发布 1.21.1 版本" |
| **给下一步** | "安装失败" | "安装失败：Java 21 未安装。点这里自动下载" |
| **数字要具体** | "文件较多，请稍候" | "1,247 / 1,834 个文件 · 剩余约 24 秒" |
| **不用技术黑话** | "inheritFrom 链合并失败" | "版本配置合并出错，请尝试重新安装" |
| **错误要可行动** | "Exception in thread main" | "内存不足。当前分配 2 GB，建议提高到 4 GB" |

**术语统一表**（避免同一概念多种叫法）：

| 概念 | 统一用词 | 不要用 |
|---|---|---|
| 一套独立游戏环境 | **实例** | 配置、档案、profile、版本 |
| 提供 Mod 运行环境的框架 | **加载器** | modloader、Mod 加载器、框架 |
| Mod 的整合发行包 | **整合包** | 模组包、modpack |
| Java 运行环境 | **Java** | JRE、JDK、运行时（首次提到可注明"Java 运行环境"） |
