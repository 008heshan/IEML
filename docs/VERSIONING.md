# IEML 版本号规则（SemVer + 阶段后缀）

> 这份文件是**唯一的版本号依据**。改版本号之前先读这里。
> 用户给的原始表格在第二节，原样保留。

## 一、为什么要写这份文件

以前版本号是**手填**的，而且**三个地方各填一份**：

| 文件 | 字段 | 本轮之前的值 |
|---|---|---|
| `package.json` | `version` | `0.2.0` |
| `src-tauri/Cargo.toml` | `[package] version` | `0.2.0` |
| `src-tauri/tauri.conf.json` | `version` | `0.2.0` |
| 桌面快捷方式 | 文件名 | `IEML 启动器.exe`（名字里没有版本） |

三个 0.2.0 看起来是一致的，但它和"这个启动器实际上处于什么阶段"毫无关系 ——
`0.2.0` 按下面的规则读作"**第二个公开稳定版**"，而这个项目连第一次公开测试都没到。
版本号一旦开始说谎，后面所有"这个 bug 是哪个版本引入的"都无从谈起。

所以规则固定下来，并且**用一个脚本同步**（`tools/set-version.mjs`），
不允许再手填三份。

## 二、阶段表（用户给定，原样保留）

| 阶段 | 版本号示例 | 含义 | 谁用 |
|---|---|---|---|
| 内部开发 | `0.1.0-dev.1` | 代码没写完，随时会崩 | 只有你 |
| 小范围测试 | `0.1.0-alpha.1` | 核心功能能跑，但缺功能、有 bug | 熟人、内测群 |
| 公开测试 | `0.1.0-beta.1` | 功能基本完整，找 bug | 所有愿意试的人 |
| 发布候选 | `0.1.0-rc.1` | 只修 bug，不加功能 | 等正式版的人 |
| 正式发布 | `0.1.0` | 第一个公开稳定版 | 所有人 |
| 核心稳定 | `1.0.0` | API 稳定，插件系统就绪 | 生态开发者 |

## 三、怎么用（可执行的规则）

### 3.1 形状

```
<主>.<次>.<修订>[-<阶段>.<序号>]
```

* **有后缀** = 不是稳定版。`0.1.0-dev.3`、`0.1.0-beta.2` 都读作"不是给人用的正式版"。
* **没后缀** = 正式发布。`0.1.0` 是第一个公开稳定版，`1.0.0` 是 API 稳定版。
* 阶段顺序（低 → 高）：`dev` < `alpha` < `beta` < `rc` < 正式。

### 3.2 什么时候动哪一位

| 改动性质 | 动哪一位 | 例子 |
|---|---|---|
| 修 bug、改文案、补测试 | 阶段序号 +1 | `0.1.0-dev.2` → `0.1.0-dev.3` |
| 加功能（同一个目标版本内） | 阶段序号 +1，**并把序号重置**（如果刚跨阶段） | `0.1.0-alpha.4` → `0.1.0-beta.1` |
| 进下一个阶段 | 换阶段名，序号回 1 | `0.1.0-dev.9` → `0.1.0-alpha.1` |
| 正式发布 | 去掉后缀 | `0.1.0-rc.3` → `0.1.0` |
| 破坏性改动（存档/配置格式不兼容） | **主版本** +1 | `0.1.0` → `0.2.0` |
| 加功能但向后兼容 | **次版本** +1 | `0.1.0` → `0.2.0`（0.x 阶段次版本当主版本用） |

> **0.x 阶段的约定**：主版本为 0 时，任何东西都可能变，
> 所以"破坏性改动"走**次版本**（`0.1.0` → `0.2.0`），修订位只修 bug。
> 这与 SemVer 官方对 0.y.z 的规定一致。

### 3.2.1 1.0.0 之后怎么走（★★ **用户 2026-09-27 定**，之后一律按这条）

> 用户原话：
>
> > 到时候，第一个正式大版本定 1.0.0，小修小改 1.0.x，大修大改 1.x.0，
> > 下一个大版本 x.0.0。X 为要改的版本号位，可以叠加到两位甚至三位。

翻成人话就是三句话：

| 改动性质 | 动哪一位 | 例子 |
|---|---|---|
| **小修小改**（修 bug、改文案、补判据） | **修订位** +1 | `1.0.0` → `1.0.1` → … → `1.0.10` |
| **大修大改**（加功能、行为变化，向后兼容） | **次版本** +1，修订位归零 | `1.0.7` → `1.1.0` |
| **下一个大版本**（不兼容、或攒够了整代） | **主版本** +1，后两位归零 | `1.4.2` → `2.0.0` |

* **第一个正式大版本是 `1.0.0`**（不是 `0.5.0`，也不是 `0.10.0`）——
  它同时意味着"从 0.x 毕业"：**不许带阶段后缀**（`1.0.0-rc.1` 只是它的候选，不是它本身）。
* ★ **只许动一位，低位一律归零**（`1.2.3` 的下一个是 `1.2.4` / `1.3.0` / `2.0.0` 三选一）。
  这条现在只靠人守：`--bump` 按上表算下一个号，手写的号只过形状校验 ——
  跳号或"两位一起动"不会报错，得自己对着上面那张表核。
* ★ **位数不封顶**：`1.0.10`、`1.12.0`、`1.0.123` 都合法 ——
  攒到两位三位是**正常积累**，不是错误，所以**不许为了对齐而补零或跳号**
  （`1.0.09` ✗ 前导零；`1.0.11 → 1.1.0` 只是为了好看 ✗）。
* `0.x` 阶段（当下）仍然按 §3.2 与上面那段 0.x 约定走；**推出 1.0.0 的那一天起**，
  本节就是唯一口径。

> ★ 怎么改：`node tools/set-version.mjs --bump patch|minor|major`
> —— 它按上表算出下一个号再写进所有落点（手算容易多进位一位）。
> 手写完整版本号也允许（`node tools/set-version.mjs 1.0.0`），但一样要过形状校验。

### 3.3 阶段是怎么判定的（不要凭感觉）

| 阶段 | 进入条件（**全部**满足才能进） |
|---|---|
| `dev` | 默认状态。只要还有"已知会挡住用户的事"没解决，就在这里 |
| `alpha` | ① 能从零装一个版本并真跑起来；② 崩溃能给出原因；③ 没有"点了报成功但什么都没发生"的功能 |
| `beta` | 见下面「beta 的判据（2026-09-20 重写）」 |
| `rc` | 见下面「rc 的判据」—— **只修 bug 不再加功能**，且清单全绿 |
| 正式 | 用户能不看文档自己装好并玩上 |

#### 正式版的判定（**2026-09-26 定型**，`0.1.0`）

正式那一档的进入条件只有一句：**用户能不看文档自己装好并玩上**。这一天的判定依据：

| # | 依据 | 证据 |
|---|---|---|
| 1 | rc 判据 1–4 全绿 | 见上表（① 已收口、② 当天扫清、③ 用户 09-21 亲手验过、④ 门禁 **33 项** + 发布自检） |
| 2 | **两个**干净的 rc 周期都真的走完 | `rc.11` → `rc.12` → `rc.13`：每个都做了「升版 → 签名构建 → 部署到桌面（逐字节校验）→ 发布到 CNB → `verify-endpoint` 按客户端方式复验」。期间**没有新的 P0**；`rc.13` 与 `rc.12` 功能相同，只为把第二个干净周期走完 |
| 3 | 更新通道端到端可用 | 每次发布都实测：匿名拉 `latest.json` → 下载安装包 → **用编进 exe 的 pubkey 验签通过**（`tools/release/verify-endpoint.mjs`）；旧发布仓那座桥的 7 条判据也每次复验 |
| 4 | "不看文档也能装" | 安装包双击即可（NSIS，`currentUser`）；启动器**不需要填任何东西**（CF 走镜像、Java 自动探测/下载）；README 的「快速开始」只有三行命令，是给开发者的，玩家不需要读 |

只发 Windows；**安装包没有 Authenticode 代码签名**（首次运行可能有 SmartScreen 提示，
实测 `NotSigned`）；Java 自动下载只有 Adoptium 一条路；**没有 CI**（33 项门禁在本机跑）；
备份/回滚、拖拽导入、CF 整合包自动安装这三件**没做**（README 里也没承诺）。

历史记录：`dev.1` ~ `dev.14` 期间一直停在 `dev`，因为每轮都还有"已知会挡住用户的事"没解决；
`dev.12` 之前这份文件写着"下一步应该进 alpha" —— 实际上 `alpha` 的三条在 dev.5 就满足了，
那句话在这一轮一并更正（**旧结论错了就改，不改就等于继续误导**）。

### 3.4 改了版本号要动哪些地方

**只跑一条命令**（它会把所有位置改成同一个值，并打印改了什么）：

```bash
node tools/set-version.mjs 0.1.0-dev.13
node tools/set-version.mjs --check    # 只校验一致性（pnpm verify 里跑）
```

它负责**改写**这些位置：

1. `package.json` → `version`
2. `src-tauri/Cargo.toml` → `[package] version`（**必须**，`app_info` 命令读的是它）
3. `src-tauri/tauri.conf.json` → `version`（Tauri 打包器读这个，决定安装包名字）
4. `src/domain/version-info.ts` → 前端的 `APP_VERSION`（关于页显示用）
5. `README.md` → 开头的「当前版本」与安装包文件名示例

> ★ 第 5 条是 2026-09-14（dev.12）补上的。在那之前 README 不在表里，
> 于是它漂移了**八个版本**都没人发现（代码是 dev.11，README 还写着 dev.3）。
> 教训：**说"当前版本"的地方就是版本号的落点**，漏一个就等于没有同步。

★ **开发记录不进仓库**（用户 2026-10-09 定：「所有开发日志、记忆之类的都不要，
我们只存对启动器有用的」+「记忆，日志之类的，只在本地存」）——
每轮改了什么、为什么这么改，只写在本机的开发记录目录里，仓库不留副本，
所以这个脚本既不写、也不校验任何"变更记录"文件；
`--check` 只管上面那五个落点是同一个号、且号的形状合规。

跑完必须重新构建，否则 exe 里还是旧版本号。

### 3.5 为什么 `app_info` 读的是 Cargo 的版本

`src-tauri/src/commands.rs`：

```rust
version: env!("CARGO_PKG_VERSION").into(),
```

`env!` 是**编译期**展开的 —— 改了 `Cargo.toml` 不重新编译，界面上的版本号不会变。
所以"改了版本号"和"重新打包"必须成对出现（`pnpm desktop:build` 会做这件事）。
